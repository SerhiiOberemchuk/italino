# Тижневий цикл доставки Італія → Україна

Це логістична модель, навколо якої побудовано сайт. **День відправки —
неділя** (підтверджено власником 2026-09-17). Дедлайн прийому замовлень і
терміни доставки нижче — **припущення, які треба підтвердити**
(див. [PROJECT.md → Відкриті питання](PROJECT.md#відкриті-питання-потрібне-рішення-власника)).

## Цикл одного тижня

| Момент | Подія | Що бачить покупець |
| --- | --- | --- |
| Сб 00:00 – Пт 18:00 | Прийом замовлень у поточну поставку | Банер «Наступна відправка — нд, DD місяця. Замовляйте до п'ятниці 18:00» + зворотний відлік |
| Пт 18:00 | **Дедлайн (cutoff).** Замовлення після нього потрапляють у наступну поставку | Банер перемикається на наступну неділю |
| Сб | Викуп решти речей в Італії, комплектація | Статус «Комплектуємо в Італії» |
| **Нд** | **Відправка з Італії** | Статус «Відправлено з Італії», лист/повідомлення |
| Нд + 4–6 днів | Прибуття в Україну, митне оформлення, передача в Нову Пошту | Статус «В Україні», з'являється ТТН |
| + 1–2 дні | Доставка у відділення/поштомат/кур'єром | Статус «У відділенні» → «Отримано» |

Разом від дедлайну до дверей: **≈ 7–11 днів**, від відправки — **5–9 днів**.
На сайті використовуємо формулювання «5–9 днів від відправки».

## Розклад у коді

Розклад описано одним об'єктом у `src/lib/shipping/schedule.ts`:

```ts
export const SHIPPING_SCHEDULE = {
  timeZone: "Europe/Kyiv",
  cutoff: { weekday: 5, hour: 18, minute: 0 }, // п'ятниця 18:00 (припущення)
  dispatchWeekday: 0,                          // неділя (підтверджено)
  transitDays: { min: 5, max: 9 },
};
```

Функції `nextCutoff()`, `nextDispatch()`, `estimatedArrival()` рахують дати з
урахуванням часового поясу Києва. Зміна дня/часу — це зміна однієї константи;
усі банери, відлік і тексти читають її.

Пізніше розклад варто перенести в CRM (custom field або налаштування
workspace), щоб команда могла посунути відправку на святковому тижні без
деплою.

## Статуси замовлення

Публічний API Obriym CRM повертає статус замовлення з фіксованого списку.
Сайт показує покупцю **свої** формулювання:

| Статус у CRM | На сайті | Коли |
| --- | --- | --- |
| `pending` | Прийнято, очікує підтвердження | одразу після checkout |
| `confirmed` | Підтверджено, у поставці від DD.MM | менеджер підтвердив; оплата отримана або обрано накладений платіж |
| `processing` | Комплектуємо в Італії | після дедлайну |
| `shipped` | Відправлено з Італії / В Україні (коли є ТТН) | день відправки; ТТН з'являється після прибуття |
| `delivered` | Отримано | НП підтвердила вручення |
| `cancelled` | Скасовано | за запитом покупця або якщо речі немає в наявності |
| `refunded` | Повернено кошти | після повернення |

ТТН і трекінг беруться з `GET /api/v1/orders/{externalId}/shipments`
(`carrier: "nova_poshta"`, `trackingNumber`).

## Крайові випадки

- **Замовлення після дедлайну.** На checkout показуємо явно: «Це замовлення
  поїде поставкою від DD.MM (наступна неділя)».
- **Речі немає в наявності в Італії.** Менеджер скасовує позицію в CRM
  (`PATCH /orders/{externalId}/items/{itemId}` або скасування замовлення);
  покупець отримує повідомлення і повернення передоплати.
- **Святковий тиждень / пропуск відправки.** Тимчасово — зміна константи
  розкладу; цільове рішення — розклад у CRM.
- **Обмін розміру.** Повернення приймається в Україні, обмін їде з наступною
  поставкою. Політика 14 днів — припущення.

## Комунікація з покупцем

Кожна зміна статусу — повідомлення на e-mail (і, за бажанням, Telegram):
підтвердження замовлення з датою відправки → відправлено з Італії → ТТН
Нової Пошти → отримано (запит відгуку). Реалізація сповіщень — на боці CRM
(webhook або server function); сайт лише показує стан.
